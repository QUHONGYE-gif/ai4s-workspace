# 蛋白质设计中间产物与复用加速分析

整理：陈铠洲　依据：2026 年 10 月 21 日实际实验及固定版本源码　更新：2026 年 10 月 22 日

## 结论与讨论范围

蛋白质设计不只产生最终结构，还留下骨架、序列概率、数据库、搜索候选、MSA、预处理数据和置信度等产物。这些文件既帮助理解和检查过程，也可能让后续计算省去部分重复工作。**能复用什么，取决于新任务是否仍满足原产物的使用条件，不能只看文件名或目录是否存在。**

本次已实际使用 RFdiffusion 的 IGSO3 数值表缓存、复用已建 Swiss-Prot 目标库，并将已有设计序列接到 GPU 搜索分支。已核实工具中存在若干缓存与跳过行为，但没有完成缓存开关对照或正式加速比实验。当前全流程脚本没有自动跨运行匹配和复用科学结果的功能。

本文面向团队解释“产生什么、怎样复用、何时不能复用、可能省在哪里”。它也是陈铠洲与曲鸿烨讨论的材料，尚未形成双方确认的复用策略、分工或评价方案。文中的建议是 Codex 根据本次观察整理的候选，不应作为团队既定决定或研究收益引用。

## 给团队的阅读与汇报方式

这份报告不是新的实验结果清单，而是帮助团队判断“下一次哪些工作可以接着用、哪些必须重算”的讨论材料。第一次接触流程的队友可以先按以下顺序阅读：

1. 先读第 1 节，认识骨架、序列、数据库、MSA、预测结构和日志分别是什么。
2. 再读第 2 节，区分本次已经实际观察到的复用行为、没有命中的结果，以及尚未测量的收益。
3. 最后按第 3–6 节查某一类产物的使用条件、失败风险和可能的加速方向。

汇报时建议先讲一条具体链路：**已有骨架可以交给 ProteinMPNN 生成新序列；已有精确序列可以重新搜索或直接接 Boltz；已有固定数据库可以服务多个查询；A3M 只有在查询序列和搜索条件仍匹配时才可能复用。** 然后再说明本次 CPU/GPU 结果不同、设计序列无命中，以及为什么不能把“文件存在”当作“结果可复用”。

报告中的内容分为三种状态，阅读时要分开：

- **已验证事实**：本次确实运行过，并有文件、日志、哈希或检查结果支持。
- **工具机制**：从固定版本源码或官方说明确认存在，但不等于本次测出了收益。
- **协作建议和待确认事项**：用于下一次共同设计实验，不能在汇报中说成已经采用的方案。

如果只记住一个判断原则，应记住：**复用必须同时核对输入内容、来源、参数、工具版本和完成状态；哈希能证明文件没有被改写，但不能证明生物学结论正确。**

## 1 先认识流程中留下的数据

### 1.1 从一条设计流程看产物来源

本次流程是：RFdiffusion 生成一个 80 aa 单链骨架 → ProteinMPNN 为它设计序列 → MMseqs2 搜索 Swiss-Prot 并生成 MSA → Boltz 根据序列和可选 MSA 预测结构 → 检查与可视化。

骨架是主链形状，序列是氨基酸排列，MSA 是多条序列按位置排齐的结果。预测结构是模型根据输入重新给出的坐标，不是实验测得结构。每阶段都有独立输入与输出，因此既可以从头运行，也可以在输入来源清楚时从中间接续。

| 阶段 | 主要产物 | 为什么值得保存 |
| --- | --- | --- |
| 部署 | 权重、依赖清单、源码版本、修复日志 | 说明实际用了什么，也减少重复准备 |
| RFdiffusion | 骨架 PDB、.trb、两类轨迹、IGSO3 数值表 | 分别用于下游设计、解释生成条件、观察过程及数值表复用 |
| ProteinMPNN | 设计 FASTA、概率 NPZ、评分 NPZ | 序列交给搜索/预测；概率和评分供分析 |
| MMseqs2 | 源 FASTA、普通/padded 库、查询/结果/临时库、TSV、A3M、筛选摘要 | 固定搜索范围，追溯候选怎样进入预测 |
| Boltz | YAML、processed、PDB/CIF、置信度、pLDDT/PAE/PDE | 解释预测输入、保留预处理与可分析结果 |
| 检查与展示 | checks、运行清单、日志、图片、PyMOL 脚本 | 证明文件连接、保存经过、协助团队理解 |

本次实际保留了所有 GPU 分支中间文件类别，最终清单为 201 普通文件、5 符号链接。它们包含成功分支、失败验收分支、数据库与临时数据；不是只打包最终 PDB。

### 1.2 用一个例子理解复用

如果已有一个骨架，想在它上面生成三条不同序列，可以把同一个 PDB 多次交给 MPNN，省去再生成骨架。但改变温度或种子后需要真正采样，不能把旧序列直接返回并说完成了新的设计。

如果已有一条确定序列的合格 A3M，想改变 Boltz 采样种子做结构预测，可以复用这份 A3M，省去搜索；预测仍需重新做。如果序列改了，则旧 A3M 通常不能直接沿用。

这里要区分三种用途：保留文件供解释，省去重复准备，以及把适用的旧计算结果用于新请求。一个文件值得归档，不等于它已经能作为推理缓存；有临时状态也不等于能从任意位置续算。

## 2 本次实验实际提供了什么证据

### 2.1 已经观察到的复用行为

首次手工设计生成骨架、序列、单序列预测和 PyMOL 图，明确了三个模型之间的文件边界。初次 CPU 搜索又生成目标库、命中表和 A3M，使搜索成为可单独检查的阶段。

后续 CPU 封装重新生成另一套骨架和序列，复用此前已建的目标库；RFdiffusion 日志出现 Using cached IGSO3.，说明实际加载了已有数值表。GPU 补充则直接读取封装设计的 FASTA，不重跑上游；同一个 padded 目标库被用于设计和天然蛋白两条查询。

| 观察 | 已验证到哪一步 | 不能由此推出什么 |
| --- | --- | --- |
| 加载 IGSO3 表 | 有缓存命中日志 | 未测省时，也不是复用旧骨架 |
| 再次使用普通目标库 | CPU 封装完成搜索与预测 | 不是缓存命中表，也未验证大型预建索引收益 |
| 同库查询两个对象 | GPU 两查询均成功 | 不是复用查询结果；查询结果各自生成 |
| 已有设计 FASTA 续接 | GPU 从第二条设计序列开始运行 | 没有自动缓存匹配，也没有自动策略收益评测 |
| 天然 A3M 接入 Boltz | 初次 CPU 和 GPU 天然对照完整预测成功 | 未验证设计功能或 MSA 效果提升 |

两次 80 aa 设计是不同对象；首次手工叠合 RMSD 0.827 Å 不能用于封装设计。天然人血红蛋白 α 链 P69905 为 142 aa，它来自已有数据库，用于验证搜索有命中和带 MSA 的预测路径，不是 MPNN 设计结果，也不能将其 MSA 用在设计序列上。

### 2.2 CPU 与 GPU 的差异为什么影响复用

严格 CPU 与 GPU 搜索都用同一 P69905 查询、同一 Swiss-Prot 源快照，E 值上限 0.001、一致性至少 0.3、查询覆盖至少 0.8、候选上限 500、10 线程，保留回溯并显式计算一致性。但 CPU 用 -s 7，GPU 用 --gpu 1 且不传 -s，采用最高灵敏度。

| 结果 | 严格 CPU | GPU |
| --- | ---: | ---: |
| 命中目标数 | 498 | 498 |
| 两后端共有目标 | 487 | 487 |
| 各自独有目标 | 11 | 11 |
| 原始 A3M 含查询 | 499 | 499 |
| 筛选 A3M 含查询 | 464 | 467 |
| 对应下游验证 | Boltz 解析与 MSA NPZ，无新完整预测 | 完整带 MSA 预测成功 |

因此，同序列、同源库、同数量仍可能得到不同内容。搜索后端、工具构建、灵敏度与筛选规则都应记入结果适用条件。多三条 A3M 记录不是质量更好的证据；本次未算 Neff，也未做同条件结构质量对照。

初次 CPU 使用较宽松设置，没有显式 0.3/0.8 筛选与精确一致性计算，天然 A3M 为 501 条并完成预测；它也不能与后来 464 或 467 条的结果当作相同请求互换。

### 2.3 没有命中也需要记录

两次设计在本次库与各自参数下均无命中，A3M 只有查询，Boltz 实际用 msa: empty。无命中是有范围的负面结果；它并不意味着所有数据库都无同源，也不意味着检索工具失败。

在精确查询、数据库快照和搜索条件完全一致时，可以考虑重复使用这个无命中结论。换库、改阈值或换后端后，需要重新判断。本次没有实现这种自动复用。

## 3 每类产物怎样复用 有哪些条件

### 3.1 环境 权重与数值表

权重和安装好的环境可服务于多次任务，主要减少下载与部署。核对平台、驱动、依赖、源码和权重身份后才能使用；本次两套环境的存在本身不是兼容保证，实际还处理了 DGL/CUDA 和 PyTorch 问题。

IGSO3 表是 RFdiffusion 旋转扩散需要的数值查找数据，同一适用参数与实现下可以重复加载。它既不是目标骨架，也不是完整采样状态。修改调度或实现时应重新核对，不因名称相同直接复用。

### 3.2 骨架与序列设计产物

| 产物 | 合理用法 | 要核对的条件 |
| --- | --- | --- |
| 骨架 PDB | 固定骨架，多次改变 MPNN 采样设置 | 坐标内容、链、残基编号、设计约束 |
| .trb | 解释实际配置与残基映射 | 与同一个骨架和源码对应 |
| 轨迹 PDB | 看形状形成过程、分析中间几何 | 轨迹来源与步骤含义；不是独立最终候选 |
| 设计 FASTA | 同序列尝试不同搜索/预测条件 | 精确序列、链、来源骨架；选对 sample 记录 |
| 概率/评分 NPZ | 分析位置偏好与同条件候选 | 骨架、模型、约束、解码与序列条件 |

本次没有验证由 .trb 或轨迹恢复任意步骤，也没有验证将保存概率当作完整模型状态直接重新采样。要增加新候选，应执行相应模型；保留旧序列只是供后续分支使用。

### 3.3 数据库与 MSA

一份固定目标库可以供许多查询使用，省去反复下载、解压和 createdb。GPU padded 库还可省去重复转换，但普通库与 padded 库是不同文件组，不能只改前缀互换。

A3M 是最直接的搜索与预测交接物。复用它应核对精确查询和链、数据库快照、搜索后端/工具、参数、导出与筛选规则，并确认首行、列数和记录完整。序列变了或条件不符时，不能因“名称仍叫 design”沿用旧 MSA。

本次对设计和天然对照生成各自 A3M。天然蛋白能检出候选，只证明该查询路径成功，不能替另一条设计提供进化信息。目标库复用与 A3M 复用节省的是不同步骤，应分别统计。

### 3.4 Boltz 预处理与预测结果

processed 保存解析后的输入。输入及解析版本兼容时，可能省去重复解析和特征准备；但必须核对 YAML 全内容、序列、链、MSA 内容、模板、约束和配体，不能只看记录 ID。

最终结构与置信度可以直接用于同一结果的展示、叠合与后续分析。如果请求的是新的随机样本，改变了模型、种子、recycles 或 sampling steps，则需要新预测，不能把旧结构当作新样本。

PyMOL 图片和脚本可重复用于讲解，但图片不代替原始坐标、残基映射和数值。结构来源改变后应重做相应叠合与着色。

## 4 工具自身已有的缓存与跳过机制

### 4.1 RFdiffusion

固定版本源码会把 IGSO3 数值表写成 pickle，已有表则加载；模型运行器传入数值表缓存位置。本次日志确实出现命中。表名包含部分调度参数，但没有完整的源码与参数内容校验，因此共享前仍需核对适用条件。

另有 inference.cautious：同名 PDB 存在时跳过；design_startnum=-1 可以顺延编号。这属于文件存在性判断，没有同时证明请求相同或配套 .trb 完整，不能自动等同于正确的科学结果缓存。

### 4.2 ProteinMPNN

官方 CLI 可在一次模型加载后处理多条样本或骨架，并支持 score-only、条件/无条件概率等模式，保存 score/probs。本次路径没有发现跨独立 CLI 请求的持久科学结果缓存。

批量采样可能减少重复初始化，但仍需产生新样本并验证数量和内存；它与直接读取旧 FASTA 是不同操作。本次封装只实跑过单骨架单序列。

### 4.3 MMseqs2

目标库本来就可供不同查询重复搜索，本次普通库和 GPU padded 库都实际重复使用。createdb 不等于预建大型 createindex；本次没有测量 createindex 的空间和收益，也未使用 gpuserver。

query、hits、alignment、pref_0 和 blastp.sh 等内部文件有追溯价值。本次保留它们，但没有验证任意临时目录都能安全续算；重新运行还受到工具版本、输入、参数及中间状态影响。

### 4.4 Boltz 2.2.1

模型权重和分子资料下载到 cache，已有文件可以省去重复下载；--cache 或 BOLTZ_CACHE 控制位置。这种下载缓存不省去模型前向推理。

源码还会根据 processed record ID 跳过已有预处理；存在 MSA NPZ 时可以跳过解析；预测筛选会根据 predictions 下已有目标目录跳过预测。主要判断依据是 ID 或路径存在，未完成对新输入内容的全面核对。

这带来一个实际协作风险：同名 YAML 或 A3M 改了，旧 processed 仍可能被使用。--override 改变预测跳过行为，不等于清空全部旧预处理。本次控制脚本采用新输出目录，避免把同名旧输入误当作当前结果。

### 4.5 三个层次要分别说明

源码中存在缓存分支，是机制事实；日志显示读取缓存，是实际使用事实；比重新计算更快且仍正确，是需要对照实验的结论。本次前两类有证据，尚无第三类正式收益结论。控制脚本也没有实现跨运行科学产物的全局自动缓存。

## 5 从本次错误得到的协作要求

### 5.1 文件名相同不代表内容与请求相同

本次先后设计两个对象，又改变搜索筛选和后端。同名 design、同样 80 aa、相同候选数都不足以确认同一个结果。建议为可复用对象保存输入内容或哈希、来源、参数、版本、种子及状态。

| 拟复用对象 | 建议保存的最小信息 | 完成检查 |
| --- | --- | --- |
| 骨架 | PDB 哈希、链/残基映射、设计条件 | 坐标可读、长度符合、与元数据匹配 |
| 序列 | 精确序列与链、骨架来源、模型/配置/种子 | 选中采样记录，搜索与预测使用同一条 |
| 目标库 | 源 FASTA 哈希、工具构建、建库命令、配套文件哈希 | 类型/索引/头库完整，padded 来源明确 |
| A3M 或无命中 | 查询、库身份、后端/参数、导出与去重规则 | 首行、列数、数量、下游采用状态可追溯 |
| Boltz 预处理 | YAML、A3M 哈希或 empty、解析版本 | 对应当前输入且数据可读 |
| 最终预测 | 上述输入、模型/权重、采样/循环、种子、环境 | 数量/序列正确、置信度有限、NPZ 完整 |

这是供共同讨论的建议，不是已实施的缓存协议。哈希证明字节身份，不证明生物学有效或跨硬件逐位复现。

### 5.2 失败现场和完成状态必须保留

本次遇到依赖不兼容、Hydra 生成目录触发预检、辅助小数参数报错，以及 GPU 验收漏找输出层级。尤其 GPU 曾出现搜索与模型退出 0、整体验收仍失败的情况，说明不能仅凭退出码或目录存在判断可复用。

失败目录与修正后的新目录分别保留，成功状态要以具体文件检查为依据。早期建库与交互搜索有日志覆盖，原结果/tmp 和重试记录仍在，但不能声称每份历史日志原件都完整。未来独立命名日志和记录每次尝试有助于减少这种信息损失。

### 5.3 保存成本与共享状态

本次 Swiss-Prot 575,748 条，压缩源 93,801,562 字节，解压 288,201,213 字节。GPU 普通库文件组 317,583,909 字节，padded 组 319,799,125 字节；GPU 全部保留普通文件合计 638,444,528 字节，完整压缩包 270,256,012 字节。这是本次快照的实测，不是未来版本的固定大小，也不含全部模型环境成本。

保留什么应比较重建、读取、传输和存储成本。当前未测这些对照，轨迹和 tmp 是否长期保留尚未决定；本次未删除既有材料。

主要归档已由陈铠洲回传核验，并在平台持久卷备份，尚无团队共享下载链接。两份关机补充包仅在平台持久卷：ai4s-shutdown-extra-20261022.tar.gz 含 CPU DB/tmp、精确 GPU 工具包等；ai4s-source-generated-20261022.tar.gz 含 Hydra 日志配置和示例输出。正常下载被组织策略阻断，须保留网盘并经获准通道交接。恢复包也不含完整环境与所有权重，不能直接解压即运行。

## 6 可以考虑的加速方向

### 6.1 先区分省掉什么计算

| 方法 | 可能减少的开销 | 当前证据与限制 |
| --- | --- | --- |
| 保留权重、环境、数值表和目标库 | 下载、安装、表计算、建库 | 部分机制已实际使用，收益未测 |
| 同骨架批量 MPNN | 重复加载与调度 | CLI 支持，当前封装只验证单条 |
| 同序列复用合格 A3M | 搜索和比对 | 适用条件较清楚，未做自动匹配 |
| 同请求使用已有完整预测 | 重复预测 | 需确认请求与结果身份，未实现全局缓存 |
| GPU MMseqs2 | 搜索计算 | 已跑通但结果有差异，属于后端变化 |
| 兼容的 Boltz kernels | 部分推理计算 | 本次关闭，未验证 |
| 常驻模型进程、合并查询 | 重复初始化和调度 | 工程候选，未实施或测量 |
| 减步数、recycles、样本数或 MSA 深度 | 推理和特征计算 | 改变计算条件，可能影响质量 |

直接使用适用旧结果、切换 GPU 计算、减少计算量是不同方法。不能把缩小数据库、降低步数引起的时间减少统称为缓存收益；质量影响需要另做对照。

### 6.2 本次耗时能说明什么

CPU 封装一条新设计总计约 112.45 秒：RFdiffusion 38.255、MPNN 3.472、CPU search 11.035、Boltz 46.721 秒，另有预检和转换。GPU 补充从已有序列开始，两查询及其预测共 73.50 秒，搜索分别 0.510/0.470 秒，Boltz 36.303/34.501 秒。createdb 1.652、padded 转换 5.345 秒另计。

它们工作量不同，后端、灵敏度和缓存状态也未控制，不能相除得出 GPU 加速比或复用收益。没有重复计时、冷热对照、读取/传输测量或显存峰值。本次可以据此提出“预测或初始化可能值得关注”等候选问题，不能报告已验证的性能改善。

## 7 与队友共同讨论的下一步

首先需要共同确定首个复用对象。Codex 建议优先讨论精确序列、固定数据库与后端下的 A3M，或固定骨架供多次 MPNN 采样；它们的数据边界较清楚。最终选择、有效性条件和评价仍需陈铠洲与曲鸿烨确认。

建议讨论四件具体事情：

1. 新请求改变哪些条件时旧产物必须失效，尤其序列、链映射、数据库更新、工具后端与参数变化。
2. 如何标记失败、写入未完成与可使用结果，以及无命中结果的适用范围。
3. 分别测量首次生成、重复计算、读取、传输、端到端与各阶段时间，并记录缓存大小和完整性；缓存冷/热状态明确，重复测量后再报告波动。
4. 完整归档放在哪里共享、哪些文件长期保留、谁负责维护；目前尚未确定统一存储和分工。

这些是讨论候选，不是预先确定的研究协议或团队决定。后续应把双方确认的对象、适用条件、测量方法、日期和修改原因明确写下；真正执行后再报告结果。原型能工作、复用是否正确、速度是否改善和科学效果是否改变，分别检验。
