# 空间预算与删除保留策略（任务 5.0）

本轮要回答三件事：满了删什么、先删谁、删了之后怎么办；另外回答一个附加问题：这类决策要不要引入大模型 Agent。实测数据与复现命令见 [R008 实验记录](../experiments/R008-storage-budget/record.md)。

结论先给：

1. **删产物文件，不删记录**。空间几乎全在文件上，删记录换不到空间，却同时毁掉「可补回」和「可追溯」。
2. **保留策略默认用成本感知打分，LRU 作对照与降级路径**。成本数据缺失时自动退回 LRU，并在决策记录里标注来源。
3. **在线淘汰不引入大模型**，保留确定性的回收线程；模型的价值在离线调参、理由生成与偏好协商，都在热路径之外。
4. **边界**：本轮是独立模拟实验台（产物与成本为实验设定值），未接入真实 AiiDA 仓库，数字不构成真实性能结论。

## 删什么

一次结果占用的空间由四部分组成，量级差三个数量级：

| 组成 | 量级 | 删除的后果 |
| --- | --- | --- |
| 产物文件（结构、序列、模型输出） | MB ～ GB | 可重算补回，代价是可计量的时间 |
| 元数据行（节点、属性、输入快照） | KB | 毁掉「它存在过」这一事实，无法补回 |
| 请求与决策记录 | KB | 毁掉可追溯性，无法解释「为什么当时选了它」 |
| 跨成员传输副本 | MB | 可重新导出，但需要对方在线 |

只有第一项值得删。因此本轮所有淘汰都只作用于产物文件，节点标识、输入哈希、淘汰原因与状态机写在同一套元数据里保留下来。

## 怎么删

四种做法对照：

| 方式 | 空间收益 | 可追溯 | 可补回 | 判断 |
| --- | --- | --- | --- | --- |
| A 直接删节点（连同记录） | 高 | 否 | 否 | 不可用：验收要求能说明「为什么删了它」 |
| B 删产物文件、保留墓碑 | 高 | 是 | 是 | **采用** |
| C 搬到冷存储／另一块盘 | 中 | 是 | 是 | 需要额外的盘与搬运成本，本轮不做 |
| D 压缩后保留 | 低 | 是 | 是 | 结构与模型输出压缩比有限，且读取要解压，收益不值 |

B 的实现要点，缺一条就会出现「文件没了但记录说还在」或反之：

- **状态机**：`active → evicting → evicted → restoring → active`。先落库再删文件，删完再落一次库；不允许先删文件。
- **启动校正**：进程启动时按「文件是否真实存在」校正状态，把上次崩在中间态的条目拉回一致。
- **删除前后对账**：删除前记清单（指纹、大小），删除后逐项核对，缺项写日志而不是静默。
- **唯一删除入口**：`safe_unlink()` 校验目标必须位于实验产物目录内，其余任何路径直接抛错。安全边界不能靠调用方自觉。

五类不可删：被下游节点引用的、正在运行或排队中的、用户显式固定的（`pinned`）、库内唯一副本、本轮刚写入的。前四类在候选集阶段排除，第五类用于避免「刚算完就被自己挤掉」。

## 先删谁

LRU 在三处失效：

1. 只看上次使用时间，会把「体积大、重算贵、刚算完」的产物排在最前，恰好是最该留的。
2. 周期性批量任务会把长期不用但重算极贵的结果挤出，下一轮又要重算。
3. 无法表达成本差异：一个 20 s 的结果和一个 200 s 的结果在 LRU 眼里没有区别。

保留价值用四个可解释分量合成：

```
value = log(1 + f) · log(1 + c) / size^0.7 · e^(−age / 168h)
f = 1 + 复用次数，c = 重算成本（秒），size 以 MB 计
```

淘汰时按 value 升序取第一个。为避免浮点尾数导致顺序抖动，先按 0.25 粒度分档再按时间排序；每次淘汰把 value 降到配额的 85%，留出余量，避免每次请求都触发一轮删除。

两个实现坑写在这里备查：初版连续分档把所有分数映射进同一档，退化成纯 LRU，两种策略指标完全相同；初版「2 秒冷期」让结果依赖机器速度，同一条序列换机器跑出不同淘汰顺序。两处都已在实验台修正，记录里也标了。

三档配额下的四项指标见 [R008 结果](../experiments/R008-storage-budget/record.md#结果)：46 MB 档淘汰 8 → 3 次、重算耗时 385 → 195 s；配额降到 32 MB 时差距收窄，两者都在抖动，说明策略只在「配额略小于工作集」时有效。

## 要不要引入 Agent

先把两个东西分开，否则讨论会混在一起：

- **常驻回收线程**：确定性代码，按上面的规则判断，必须有。
- **大模型决策 Agent**：让模型看上下文决定删谁，本轮评估的对象。

**结论：在线淘汰不引入大模型。**

| 理由 | 具体后果 |
| --- | --- |
| 可复现 | 同输入两次调用可能给出不同排序，对照实验无法归因，也无法用「同一条件重跑」验收 |
| 可审计 | 理由由自然语言生成，无法与打分公式逐项核对；验收要求「每次淘汰能说明原因」，这里要的是可核对的数字而不是通顺的句子 |
| 时延与位置 | 写入路径需要毫秒级判断，不能依赖外部服务；模型不可用时会阻塞写入 |
| 不可逆 | 删除本身不可逆，不该再叠一层不确定性 |

淘汰本质是「输入四个数、规则确定、结果唯一」的排序问题，不需要语义理解。

模型真正有价值的四个位置，都刻意隔离在热路径之外：

1. **离线调参**：用历史访问序列搜索权重与分档粒度，产出候选参数交给人确认。
2. **理由翻译**：把 `value = 0.77，其中复用 0 次、重算 200 s、9.4 MB` 变成人话，纯展示层，不参与决策。
3. **偏好协商**：多人共享时出现「谁都希望自己的结果留下」，需要语义层面的协商，这是规则表达不了的。
4. **异常检测**：发现「某类产物总在被淘汰后立刻被重算」这类模式，提示规则本身有问题。

什么信号出现才值得重新评估：

- 真实数据上打分策略出现无法用四个分量解释的抖动；
- 出现必须理解内容才能决定的淘汰申请（例如「这两份结果语义等价，删哪个都行」）；
- 多人偏好冲突需要协商，规则无法表达优先级；
- 参数空间大到人工调不动，且离线搜索结果确实优于手调。

若真要试，最小形态是 shadow 模式：模型只输出建议、不执行删除，与打分策略并行跑两周，看一致率与分歧案例，再决定是否进入决策链。

## 未验证

- **AiiDA 侧两项行为**，直接影响实现细节：删除一个节点是否真正清空仓库对象（决定 B 能否只靠节点接口实现）、两个节点共享同一内容时删其一是否影响另一个（决定是否需要自建引用计数）。
- 真实产物的体积分布与真实重算成本尚未采集，打分权重需在真实数据上重标。
- 与 `src/ai4s_query/workbench.py` 的 `storage: {saved, evicted, skipped}` 字段尚未对接，页面存储指标仍为占位值。
- 无缓存、LRU、本项目策略三对照中的「无缓存」一组未跑（本轮只做 LRU 与打分）。
