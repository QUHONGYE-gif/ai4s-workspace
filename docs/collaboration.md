# 成员开发与协作

## 个人工作区

1. 使用管理员提供的 Coder 地址与个人账号，打开已分配的工作区。
2. 在仓库目录执行 `git status -sb`，确认使用自己的现有 `dev-姓名三字首字母` 分支。
3. 使用本人 GitHub 凭据提交和推送；Coder 账号不会自动授予仓库写入权限。

每人使用独立 checkout 和持久卷。初始化种子只用于首次创建，工作区重启不会自动拉取代码或覆盖已有修改。依赖与配置来源见 [运行要求](environment.md)。

## 日常开发与预览

- 修改前检查工作区和分支；同步前核对两端未提交内容，只传输必要文件。
- 应用在自己的容器内使用 3000 端口，启动后打开已有“开发预览”。查看改动不要求先提交或合并 `main`。
- 工作台启动、文件职责和接口见 [前后端开发](../web/README.md)；真实结构查看使用 [PyMOL 联合启动器](../tools/pymol_web/README.md)。
- 预览使用路径前缀。资源、API、重定向和 WebSocket 不硬编码域名根路径；验证页面跳转、刷新、控制台和网络请求。
- 后端改动按需重启本人启动的应用；日常代码修改不要求重建容器。已有服务占用端口时先确认归属。
- 代码和需保留的文件放在持久化位置。停止工作区后应用进程需要重新启动；删除工作区前先确认其卷和数据的保留方式。

Docker + Coder 用于开发预览，产品展示边界见 [设计草案](research_plan.md#开发与网页展示边界)。

## 汇总、会议与合并

1. 日常修改与 PR 复用自己的现有 `dev-*` 分支，PR 指向 `main`；未获明确要求不新建临时或整合分支。
2. 使用 [PR 模板](../.github/pull_request_template.md)，说明最终改动、相关验证、限制和依赖；未准备好时保持 Draft。
3. 汇总后由会议确认通过、修改后再议或暂缓，在 PR 记录结论及获批的提交或范围。
4. 只有经会议通过的范围才能合入 `main`。超出批准范围的实质改动须再次确认，测试通过或 Agent 判断不能替代批准。

管理员操作见 [部署与运维](operations.md)；返回 [仓库入口](../README.md)。
