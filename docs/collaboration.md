# 成员开发与协作

本文件维护成员登录、个人开发、页面预览和 PR／会议合并流程。管理员开户与模板发布见 [部署与运维](operations.md#成员开户)，环境版本与资源位置见 [环境说明](environment.md)，已开户名单和实测结果见 [当前状态](status.md)。

## 登录与个人工作区

1. 打开 [Coder](https://coder.my-rustdesk.xyz)，使用自己的邮箱与初始密码登录，首次登录后修改密码。成员无需建立 SSH 隧道、安装接入客户端或取得服务器 SSH 账号。
2. 打开已分配的 `dev` 工作区，等待就绪；尚未分配时使用 `server-personal` 模板创建。管理员原型模板不向普通成员开放。
3. 在网页终端执行 `cd ~/ai4s-workspace && git status -sb`，确认分支为自己的 `dev-姓名三字首字母`，例如 `dev-qhy`。遇到首字母重名时先协调唯一名称。
4. 成员使用自己的 GitHub 凭据，并在取得仓库写入权限后执行首次 `git push -u origin dev-首字母`。Coder 账号与 GitHub 账号是两套身份，开户不自动授予 GitHub 权限，也不代配个人 GitHub 凭据。

每人维护独立 checkout 和 home 卷，不在同一宿主机代码目录中轮流切分支。首次启动从管理员提供的公开 Git 种子初始化；种子已有个人分支则使用它，否则从种子 `origin/main` 创建。种子是制作时的快照，不保证包含最新提交；重启不会自动 fetch、切分支或 reset 已有代码。

## 日常开发与持久化

- 在自己的分支修改、测试、提交和推送；需要同步团队进展时，将 `origin/main` 合入个人分支并处理冲突。个人提交或测试通过不代表获准合入 `main`。
- 本地 Codex 或其他编辑器修改本地副本时，先将改动传到自己的工作区，或在个人分支推送后于工作区拉取；Coder 不自动同步本地文件。操作前检查两端未提交修改，避免覆盖。直接编辑远程工作区文件时无需同步。
- 代码、个人凭据、报告和虚拟环境放在持久化的 `/home/coder` 中；`/shared` 用于团队共享产物，不保存个人代码或凭据。容器系统目录内的临时安装不保证在重建后保留。
- 停止工作区保留 home 卷；删除工作区会销毁其管理的卷，因此删除前先推送代码并另存需要保留的文件。

个人工作区不挂载部署仓库、服务器 `.env` 或 Docker socket，种子目录只读。独立卷避免代码和 Git 状态相互覆盖；服务器管理员仍可管理这些卷，不将其视为对管理员或恶意租户的强安全隔离。具体资源上限见 [个人工作区环境](environment.md#个人工作区)。

## 开发预览

在自己的 `dev` 工作区启动应用，点击“开发预览”。查看修改不依赖 Git 提交、推送或合并 `main`。

| 按钮 | 容器内服务地址 | 权限 |
| --- | --- | --- |
| 开发预览 | `http://localhost:3000` | 普通成员仅可访问本人页面，管理员保留管理权限 |

每位成员都可以使用相同端口，因为服务运行在不同容器内。入口使用现有 HTTPS 域名的路径代理，没有发布宿主机端口、任意端口预览或通配子域名。配置唯一维护在 [个人模板](../coder/templates/server-personal/main.tf)；分析入口暂不启用。

入口不会自动启动应用。当前底座没有预装业务网页、Node.js、Streamlit 或 Jupyter，服务未启动时会提示无法连接；启动个人应用后重新打开即可。支持热更新的应用保存后可更新，静态页面刷新即可；需要重启加载代码的后端须重启本人启动的服务。

### 网页内容检查流程

开发工具与最终展示的分工以 [设计草案](research_plan.md#开发与网页展示边界) 为准。这里的“本地查看”指在成员自己电脑的浏览器中检查网页，网页服务仍运行在远程个人容器内。

1. 在自己的工作区修改前端、后端或应用配置；本地编辑的文件先同步到个人工作区，检查方式见上方日常开发说明。
2. 在容器中启动应用，使用上表的开发预览端口；修改一般代码无需每次重建容器。依赖或配置发生变化时，按应用实际需要重新安装或重启服务。
3. 在本机浏览器打开自己的“开发预览”，查看应用提供的页面、图表和科学结果，检查布局、交互、表单及页面跳转。
4. 使用浏览器开发者工具的 Elements、Console 和 Network 检查元素、错误、资源及接口请求；后端和科学任务日志在对应工作区终端查看。
5. 修改后通过热更新、刷新或重启应用再次检查，记录发现的问题和验证结果；完成后再按下方流程提交个人分支与 PR。

该流程不要求先合并 `main`，也不需要单独启用“分析页面”；图表与分析结果可以直接作为业务网页内容。若希望通过本机 `localhost` 地址访问，另需配置 Coder CLI 等本机转发客户端；这与已经提供的浏览器“开发预览”是不同的连接方式，是否完成实测以状态文件为准。

### 工作台模拟网页

[页面源码](../web/demo/index.html) 保留工作流、创建实验、个人／团队共享候选、模拟运行、产物详情和指定产物的工具会话。所有成员、科学文件、成本与权限判断均为模拟；浏览器保存备份，Python API 保存隔离的模拟快照，不连接真实计算或成员共享后端。前后端文件分工与接口见 [开发说明](../web/README.md)。当前部署位置与已验收入口见 [环境说明](environment.md#工作台模拟网页与本地-coder-cli)，完成情况见 [状态](status.md#工作台模拟网页已接入个人工作区)。

在拥有该文件的个人工作区中运行：

```bash
cd ~/ai4s-workspace
python scripts/serve_workbench.py --host 127.0.0.1 --port 3000
```

然后打开“开发预览”。应用仅向浏览器提供 `web/demo` 资源与 `/api/` 接口，不展示整个仓库。不要再用单纯的 `http.server` 启动这个页面，否则状态 API 不可用。已有服务运行时不重复启动或终止不明进程。当前 qhy 服务已经后台启动；其他成员需要取得分支代码后自行启动，不会自动变更其工作区。关闭浏览器不停止服务；工作区停止后应用进程需要重新启动，home 中的文件保留。

本机已安装本仓库独立 Coder CLI。需要新建本机转发时，在本地仓库执行：

```bash
./scripts/coder-cli.sh whoami
./scripts/coder-cli.sh port-forward qhy/dev --tcp 127.0.0.1:18080:3000 --disable-autostart
```

上述命令保持运行后，在本机浏览器打开 `http://127.0.0.1:18080/`。本轮已有转发进程，无需重复执行；遇到端口占用先核对现有进程。转发只监听本机回环地址，不发布公网端口。CLI 过期后，使用 `./scripts/coder-cli.sh login https://coder.my-rustdesk.xyz` 重新登录；配置仍留在仓库忽略目录。

建议体验“创建实验 → 检查共享候选 → 确认计划并模拟运行 → 产物详情 → 指定产物的工具会话”。页面同时提供新样本、等待共享结果及失败等演示场景。公网预览和本机转发属于不同浏览器 origin，体验记录不自动互通，可通过页面的导出／导入转移；原 `file://` 页面的记录也不会自动迁移。

### 静态页面示例

在工作区终端执行以下命令，用已有 Python 展示独立目录，不修改仓库：

```bash
mkdir -p ~/preview-pages
test -e ~/preview-pages/index.html || printf '%s\n' '<h1>我的开发预览</h1>' > ~/preview-pages/index.html
python -m http.server 3000 --bind 127.0.0.1 --directory "$HOME/preview-pages"
```

保持终端运行，点击“开发预览”。将 HTML、图片等放入 `~/preview-pages`，资源使用 `./figure.png` 等相对链接；不要把包含 `.env`、Git 凭据或私密配置的整个代码目录用作静态站点根目录。结束时在对应终端按 `Ctrl+C`，释放端口后再启动实际应用。

服务进程不随页面按钮自动启动，也不保证终端关闭后继续运行。需要后台运行时使用项目现有的进程管理方式并保存日志；工作区停止后须重新启动应用。

### 框架路径适配

入口类似 `/@csr/dev.dev/apps/preview/`，不是独立域名根路径。框架的资源、路由、重定向和 WebSocket 地址须支持该前缀，按实际入口配置 `base`、`root_path` 等选项；直接使用 `/assets/...` 或 `/api/...` 可能跳到 Coder 自身。

已完成的静态页面与代理检查不代表所有前端框架都已适配；具体业务接入时再验证路由、资源和热更新。不为尚未选定的框架预装工具或占用端口。

## 汇总、会议与合并

以下规则由用户明确确认，来源见 [用户原话](vision.md)：

1. 开发者通过面向 `main` 的 PR 汇总改动，说明目的、范围、验证结果、与其他工作的依赖或冲突以及待讨论问题；尚未准备好或会议待定时保持 Draft。
2. 团队汇总各 PR 的影响，会议明确通过、修改后再议或暂缓。
3. 在 PR 中记录会议日期、结论及通过的提交版本或范围；可以链接团队可访问的会议记录，或填写简短结论，不要求另建会议管理系统。
4. 只有完成汇总并经会议通过的改动才能合并到 `main`。未经通过不得直接推送、合并或让自动化代为合入；通过后出现超出批准范围的实质修改须再次确认。

使用 [PR 模板](../.github/pull_request_template.md) 留痕，不预设参会人数或指定合并人。CI 通过或 Agent 判断不能代替会议批准；分支保护的核查状态见 [当前状态](status.md)，文档约定不等于平台强制执行。未来共享部署规则见 [CI/CD 计划](implementation_plan.md#后续-cicd)。
