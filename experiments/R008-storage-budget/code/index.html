空间预算与删除保留策略

给结果设一个空间上限，比较两种「满了先删谁」的做法：LRU 只看上次使用时间，本项目策略看复用次数、重算成本与体积。同一访问序列、同一配额、同一初始状态各跑一遍，用最高占用、淘汰次数、淘汰后重算次数与耗时四项对齐——数字全部来自本地真实回放，不是示意。

1起点：空间有上限，删谁得有依据

50.9MB11 个产物的工作集，单次 0.9–9.4 MB
46MB主配额：工作集的 90%，装不下全部
26离线回放的访问序列长度
3 / 246 MB 配额下，两种策略的淘汰次数
①删什么
产物文件是唯一值得删的对象：单个 0.9–9.4 MB，而数据库行与请求记录是 KB 级。删记录换不到空间，却同时毁掉「可补回」和「可追溯」——所以删文件、留墓碑（指纹 + 输入 + 淘汰原因）。
②先删谁
LRU 只看上次使用时间，会把「体积大、重算贵、刚算完」的产物当成最该删的。本项目策略把复用次数 × 重算成本 ÷ 体积合成一个保留价值，价值最低的先删，再叠 7 天时间衰减。
③删了怎么办
墓碑保留原输入，再次请求时自动重算补回，并把「因淘汰多花的时间」逐笔记账（净多花 = 重算耗时 − 本来读取的 0.12 秒）。
结本轮的判断

选择成本感知的打分策略作为默认，LRU 保留为对照组与降级路径；淘汰只作用在独立实验目录里的副本上，真实结果与其他成员数据一个字节不动。

3两种策略：共用候选集，只在排序键上分叉

公平对比的前提不是「跑两次」，而是「除排序键外完全相同」。

候选集：三个共同条件
条件 1
状态为 active——已淘汰的不再进候选，避免重复记账
status='active'
条件 2
非固定项——显式标记的结果永不参与淘汰
pinned = 0
条件 3
非本轮刚写入——避免「刚算完就被自己挤掉」
fp ≠ 本次请求
第三条替代了原来「按秒计的冷期」：秒级窗口会让结果随机器速度变化，换台机器跑同一条序列就对不上。
排序键：唯一的差别
LRU最久未用先删
按 last_used_at 升序取第一个。只用到两个字段，实现 6 行。
打分保留价值最低先删
value = log(1+f) · log(1+c) / size0.7 · e−age/168h
f = 1 + 复用次数，c = 重算成本（秒），size 以 MB 计。先按 0.25 粒度分档再按时间排序，避免浮点尾数让顺序随机抖动。
软上限 = 配额的 85%：一次淘汰腾出 15% 余量，避免每次请求都触发一轮删除。
策略说明图 · 一次请求从进入到落定
为什么不用「按秒的冷期」已改
第一版用 2 秒冷期保护刚写入的产物，结果同一序列在两台机器上淘汰顺序不同。改成「本轮刚写入的不参与本轮淘汰」后，淘汰结果与机器速度无关，才能对外说「可复现」。
分档粒度写进说明坑
打分值先按 0.25 分档再排序。第一版分档函数把所有分数映射进同一档，退化成纯按时间排序——两种策略四项指标完全相同，看起来像「策略无效」，实际是分档写错了。
成本是估计值待接
cost_s 目前取实验设定值（20–200 秒），真实成本要等引擎运行记录接入。成本不可靠时策略应降级为 LRU，并在记录里标 cost_source。

6补回：删掉的还能拿回来，代价要记账

淘汰不是「结果没了」，而是「下次要多花一次计算」。

active 超配额选中 evicting 删文件写墓碑 evicted 再次请求命中墓碑 restoring 按原输入重算完成 active
墓碑保留指纹、原输入、淘汰时间与原因。补回时不需要用户重新描述任务，也不需要重新查候选——直接按记录里的输入重算。
一条真实记录（46 MB · LRU 第 16 次请求）
# restores 表
fingerprint  7ahl-mpnn-s1-n16
label        ProteinMPNN · 7AHL · seed1 · 16seq
gap_s        2.0       # 淘汰到再次请求的间隔
recompute_s  0.180     # 加速后实际耗时
cost_s       120.0     # 折算真实耗时
extra_s      119.9     # 派生：cost_s − 0.12
同一次请求在两种策略下都发生了：这个产物 9.0 MB、重算 120 秒，刚写完就被挤出去，之后又被要回来——它是本轮最贵的单次补回。
补回会再次触发淘汰
在 46 MB 状态下请求一个已淘汰的 9.4 MB 结果：占用从 41.5 MB 冲到 50.9 MB，重算完成后立刻触发 1 次新的淘汰，占用回到 41.9 MB。

这解释了为什么「重算次数」比「淘汰次数」更能反映真实代价：一次补回几乎必然带来一次新的删除。缓解手段就是候选集的第三条——刚补回的产物本轮不参与淘汰，否则会出现「补回即被自己挤掉」的抖动。
补回 200 秒新增 1 次淘汰占用回到 41.9 MB

8安全边界：只删实验目录里的副本

这条不能靠「我记得只传实验目录」，必须写在删除函数的入口上。

✓路径校验
safe_unlink() 先 resolve()，再要求目标位于 lab/artifacts/ 之下，否则抛 RuntimeError。所有删除只走这一个入口。
✓只写实验目录
产物、SQLite、会话文件全部落在 lab/；代码里没有任何指向真实仓库的路径常量。
✓不依赖他人分支
纯标准库，不 import 成本模块、运行记录或策略面板；候选口径按 main 的五级判定自实现，拼接留到下周。
✓实验前后可核对
回放前后对 ai4s-workspace 执行 git status --porcelain：无输出。本机 ~/.aiida 只有 5 KB 配置，无真实仓库参与。
删除顺序：先落库，后删文件顺序
先写 evicted 与淘汰记录并提交，再删文件。反过来的话，进程在两步之间挂掉会留下「文件已删、状态仍 active」的幽灵记录。启动时还会按文件是否真实存在校正一次状态。
实验目录占用实测
lab/ 当前 42 MB，等于当前保留产物的真实体积之和；配额 46 MB 下的峰值 45.9 MB 与 du 一致，说明写入的是真实字节，不是零字节占位。

9要不要引入 Agent：不引入大模型做在线淘汰

先把两个东西分开：常驻回收器是代码，大模型决策才是「引入 Agent」。

结论淘汰决策不用大模型，用确定性打分；保留一个常驻回收线程

「满了先删谁」本质是「输入四个数字、规则确定、结果唯一」的排序问题，不需要语义理解。推理型 Agent 在这个位置换不来更好的排序，却会同时破坏可复现、可审计和时延。真正需要 Agent 的地方在离线，而且不是现在。

四条不引入的理由
可复现
同一状态两次调用可能给出不同排序。本轮对比实验的全部结论都建立在「除策略外完全一致」上，排序一旦不确定，8 次与 3 次淘汰的差异就无法归因。
可审计
现在的每条淘汰记录都能逐项核对：哪个分量、哪个值、同批保留的对照项是谁。自然语言理由无法与公式对齐，验收时只能「听着合理」。
时延
淘汰发生在写入路径上，要在毫秒级给出结论。依赖外部模型服务意味着网络往返与不可用风险，而配额是硬约束，不能「等模型回话」。
代价
删除不可逆。在不可逆动作上再叠一层概率性判断，等于把「删错了」变成常态风险；补回要花 120–200 秒，代价明确。
模型真正有价值的位置（都不在热路径）
位置做什么现状
离线调参读历史淘汰与补回记录，建议 size 指数、衰减常数、软上限比例可选，未做
理由转述把结构化原因翻成人话给非技术用户看模板已够
多人协商成员对「谁的结果该留」有分歧时做偏好汇总未来场景
异常解释补回次数异常升高时，定位是配额问题还是序列问题可选，未做
理由转述这一项，当前的 explain() 用模板就覆盖了：「打分：价值 0.77 为当前最低（复用 0 次、重算 200 秒、9.4 MB），同批保留的 1crn-mpnn-s7-n8 价值 3.60」。这句话里每个数字都能回到记录，模型写不出更可信的版本。
什么信号出现，才值得重新评估
①规则写不下来的权衡
出现三方冲突（空间、时间、成员公平）且无法用加权公式表达，需要按情境判断时——现在只有一个目标：在配额内少花重算时间。
②策略族变多
超过 5 种策略、或需要按项目/用户动态组合，人工调参成本高于模型调用成本时。
③访问序列高度不确定
历史请求不再能代表未来，固定公式失效，需要在线学习偏好时。当前 26 次请求的模式很稳定（同一结果被反复取用）。
④有人愿意为不确定性买单
业务能接受「同状态不同结果」，并接受为审计额外建一套影子记录时。
若真要试，最小形态是 shadow 模式：模型只出建议、不执行删除，与打分策略并行记录，统计两者选择的一致率与「模型建议但规则拒绝」的样本。跑两周仍无显著优势，就不必进入热路径。
