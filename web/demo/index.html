进入工作台 看它如何判断复用

为什么需要它

同一份结果，
被不同的人反复算了很多次

AI4S 实验由预处理、模型计算和结果分析串成。中间结果数量多、生成贵，却常常只是散落在各自目录里的文件。

重复计算

队友已经生成过同样的骨架或序列，自己并不知道，只好再跑一遍 GPU。

数据搬运

结果存在别处、读取很慢时，复用反而比重算更费时，却缺少依据去比较。

来源不清

参数、模型或数据库版本改过之后，哪些旧结果还有效，只能靠记忆判断。

工作方式

改一个参数，只重算真正受影响的步骤

每一步的输出都带着身份和依赖。修改某一步之后，上游结果直接复用，下游结果重新计算。

修改：
  1. 骨架生成RFdiffusionbackbone.pdb
  2. 序列设计ProteinMPNNsequences.fasta
  3. 同源检索 · 可选MMseqs2alignment.a3m
  4. 结构预测Boltz-2structure.cif

不是更大的文件缓存，
而是读懂科学数据之后的复用判断。

使用场景

从一个人的实验，到一个课题组的共享成果

团队共享

沿用队友生成的骨架

成员甲生成并共享骨架 B1，成员乙设计新序列时直接接上，不再重复生成。

参数迭代

只重跑受影响的下游

调整 ProteinMPNN 的采样设置后，骨架照常复用，序列和结构预测重新计算。

空间整理

先预览再整理缓存

清理节点缓存前，先看能释放多少空间、共享副本是否仍在、是否影响正在运行的任务。

结构查看

从产物直接打开 PyMOL

在数据目录里选中结构文件，进入网页中的 PyMOL 会话，来源始终可追溯。

系统构成

从计算引擎到研究者的工作台

  1. 01

    工作台与 Agent

    创建实验、检查共享候选、查看数据目录；Agent 辅助接入自定义流程。

  2. 02

    查询与快照

    读取原生运行状态、文件、来源与缓存，导出为工作台可读的快照。

  3. 03

    任务编排

    两阶段工作流负责上游资格检查与连续重筛选。

  4. 04

    科学计算任务

    ProteinMPNN 计算任务校验运行记录、序列、分数与样本对应后发布结果。
